# 可靠性与失败边界

## 模型目录最大可用性

模型目录缓存采用 stale-while-revalidate：

- 内存缓存 TTL 为 300 秒。
- 过期读取立即返回最后一次有效列表，由一个后台线程刷新。
- 刷新失败后进入 30 秒冷却，期间继续返回旧列表。
- 有效列表原子写入 `GENAI_MODEL_CACHE`，重启后继续使用。
- 冷启动且没有持久缓存时，使用内置基础目录。

基础目录包含 GPT-4.1、DeepSeek V4 Flash/Pro、GLM、Qwen 3.5 和 Kimi K3。
`gpt-image-1.5` 被过滤。`GET /v1/models` 返回：

```text
Cache-Control: private, max-age=60, stale-while-revalidate=300, stale-if-error=86400
```

这个策略优先保证接口可用，代价是上游刚调整模型时可能短暂看到旧目录。

## 上游重试

网络错误以及 HTTP 408、425、429、500、502、503、504 可进入重试。明确的“模型不
存在”“节点不存在”或参数错误不会被当成临时故障。默认最多重试 10 次，退避从
0.5 秒开始，逐次翻倍并封顶 5 秒。

认证失败最多刷新一次 token。模型目录、聊天和计费请求各自使用同一类有界策略。

## 流式正确性

上游始终请求 SSE。传输层按单字节增量读取，减少短 reasoning 片段被客户端库块大小
延迟的情况。解析器支持原生 reasoning 字段和跨 chunk 的 `<think>` 标签。

无工具请求实时发送 reasoning 与正文。工具请求缓存可能属于工具语法的正文，直到
格式闭合、函数名和参数全部验证；reasoning 仍可先发送。

任何客户端增量一旦发出，本轮不再重放。这样牺牲了部分断流后的自动恢复，但保证
客户端不会把重复内容误认为新的推理步骤。GLM、Qwen 和 Kimi 连续 90 秒没有上游
字节时视为停滞，最多重试一次。DeepSeek V4 Flash/Pro 的 read timeout 是 60 秒，
最多重试两次，因此三次尝试的名义静默等待上限仍是 180 秒。这里的 timeout 是相邻
上游字节的最长间隔，不是整个请求的总时限。已经向客户端发送增量后，停滞只会产生
流内错误，不会触发重放。

## Kimi 历史清理

Kimi 历史删除是响应后的尽力而为副作用，不是生成成功条件。删除目标必须是快照之后
唯一出现、问题内容匹配的 group ID。零条或多条候选都跳过，绝不猜测。

聊天请求本身没有 `chatGroupId`。清理流程读取服务端生成的 ID 后调用历史删除接口，
清理异常只记录日志。

## 可观察性

启动日志给出代码版本、认证模式、重试配置、模型缓存路径和 Claude 别名。每个 API
请求有独立 request ID，并记录模型、是否流式、工具使用和完成耗时。

日志不会证明模型答案正确。上线观察应至少区分：

- 客户端已经收到首个 SSE 增量
- 上游正常结束
- 工具调用被完整解析
- usage 已发送
- Kimi 历史清理是否成功

## 已知边界

- stale 目录可能暂时保留上游已移除模型。
- 通用模型的 token 数可能只是兼容估算。
- 客户端已收到增量后的断流不能安全自动重放。
- Kimi 工具桥接受网页通道能力限制，不等于原生 Moonshot tool calling。
- 外层代理仍可能重新缓冲 SSE，需要单独配置和实测。
